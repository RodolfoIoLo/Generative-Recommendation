# 生成式推荐：项目三阶段全链路

> 一句话内核：**把物品变成「词」，把推荐变成「造句」。**

---

## 0. 全局：推荐被重写成了「翻译」

| | 传统判别式 | 生成式 |
|---|---|---|
| 输入 | 用户历史 | 用户历史（一串语义 ID） |
| 模型做什么 | 给目录内物品打分、排序 | 逐 token「写出」下一个物品 |
| 输出 | top-k 列表 | 物品标识符序列 |
| 输出层 | 随物品数增长 | 随语义 token 词表增长 |

三个阶段**串行**，接口明确：

| 环节 | 干什么 | 用什么 | 阶段 |
|---|---|---|---|
| ① 物品标识符构建 | 物品文本 → 分层离散码 | MiniLM + RQ-VAE / RQ-Kmeans | 第 3–4 周 |
| ② 生成式骨干网络 | 历史序列 → 自回归生成下一个标识符 | 随机初始化的 T5 式 Encoder–Decoder | 第 5–6 周 |
| ③ 约束解码与评测 | 保证生成合法、排除已见物品并形成 Top-K | 动态 Trie + Beam Search | 第 5–6 周 |

**接口**：① 的映射表是 ② 的训练词表；② 训好的模型交给 ③；③ 推理时还要回头查 ① 建好的 Trie。

---

## 1. 环节一：物品标识符构建（Item Tokenization）

### 1.1 为什么不用随机物品 ID

传统做法给每个物品分配一个整数 ID，例如 `item_4728`。它适合作为索引，但本身不携带文本语义：

- **无语义**：4728 和 4729 之间没有任何关系，模型学不到「这两个物品相似」。
- **冷启动信息不足**：新物品没有行为数据，单独的 ID 无法提供内容线索。
- **词表爆炸**：几万个物品 = 几万个独立 token，参数全花在记 ID 上。

用物品的**文本内容**生成标识符，可以让物品共享语义结构。这提供了处理冷启动物品的技术可能；当前 MovieLens 划分的 strict-cold 目标数为 0，因此本项目尚未用严格冷启动测试直接验证该收益。

### 1.2 流程

```
物品文本 → all-MiniLM-L6-v2 → 384 维单位向量 → RQ-VAE 三层量化 → 3 位量化码 + 1 位消歧码
```

- **文本编码器**：`all-MiniLM-L6-v2`，输出 384 维向量。编码阶段冻结，不参与后续 T5 训练。
- **量化器**：RQ-VAE 或 RQ-Kmeans，层数 `L`、码本大小 `K`（默认 L=3, K=256）。
- 产出：`item_id → (c₁,c₂,c₃,d)`，其中 `d` 是冲突组内消歧码。

### 1.3 关键性质

- **共享前缀 ⇒ 语义相近**。第 1 层码字捕捉粗粒度语义（如「耳机」），所以前缀相同的物品属于同一大类。
- **共享前缀的语义一致性必须实测**。当前结果显示共享 1/2/3 位前缀的物品整体上比随机物品对更相似，但不保证每一对相似物品都共享前缀。
- Trie 只需要“目录中的完整 token 路径唯一”，并不依赖每个前缀都能被人类解释。
- 组合空间是 `K^L`（指数增长）：`256³ ≈ 1677 万`，但只需训练 `3 × 256 = 768` 个码字向量。

### 1.4 码本的生命周期（什么时候用、什么时候不用）

**码本是 RQ-VAE 的可学习参数**，共 `L × K = 3 × 256 = 768` 个向量。它只干一件事：**被查最近邻**。

一次查询的完整过程：

```
输入 z（RQ-VAE Encoder 输出的 32 维潜向量）
  ├ 第 1 层：z 与码本1 的 256 个向量算距离 → 最近的是 137 号
  │          记 i₁ = 137，取 c₁ = 码本1[137]；残差 r₁ = z − c₁
  ├ 第 2 层：r₁ 与码本2 的 256 个向量算距离 → 最近的是 42 号
  │          记 i₂ = 42，取 c₂ = 码本2[42]；残差 r₂ = r₁ − c₂
  └ 第 3 层：r₂ 与码本3 的 256 个向量算距离 → 最近的是 88 号
             记 i₃ = 88，取 c₃ = 码本3[88]
输出三位量化码 (137, 42, 88)；重建 z' = c₁ + c₂ + c₃ ≈ z
```

**使用时机**：

| 阶段 | 码本参与吗 | 说明 |
|---|---|---|
| ① 训练 RQ-VAE | 是，在更新 | 重建损失 + 码本损失 + commitment 损失 |
| ① 批量给物品发 ID | 是，在查询 | 跑一遍上面的过程，存成映射表 |
| ② 训练生成模型 | 否，已冻结 | 只用映射表，码本不参与 |
| ③ 推理推荐 | 否 | 生成 token 序列后查表反解 |

**关键结论**：码本只在环节 ① 用。映射冻结后，生成模型训练和当前目录内推理只读取四位 ID 与反查表，不再调用量化器。

**但码本必须留着**：推理时如果出现一个没见过的新物品，还得用它现场算标识符。这正是「冷启动能力」的技术实现方式。

**常见的理解混淆**：把「码本」和「标识符」当成一回事。实际上码本是**工具**（尺子），标识符是**产品**（量出来的读数）。尺子只在量的时候用；量完记下读数，之后看读数就够了。

### 1.5 本环节的坑

- **码本塌缩**：少数码字吃掉几乎所有物品，多数码字从未被选中。成因是编码器与码本互相偷懒的正反馈（只有被选中的码字才拿到梯度）。
  - 检测：码字利用率、perplexity（`exp(熵)`，理想接近 K）、标识符冲突率。
  - 缓解：commitment loss、死码字重启、EMA 更新、k-means 初始化。
- **标识符冲突**：不同物品拿到完全相同的 token 串。冲突率必须统计。
- **RQ-Kmeans vs RQ-VAE**：RQ-Kmeans 是已完成的对照；最终主方案采用“连续 AE 预训练 → 潜空间残差 K-Means 初始化 → 联合训练”的 RQ-VAE。
- **文本贫瘠的数据集**（如 MovieLens 只有片名+类型）会导致语义标识符质量上不去 —— 这是数据问题不是方法问题，报告里要讲清楚。

## 2. 环节二：生成式骨干网络

### 2.1 序列构造

Encoder 端把用户历史的四位语义 ID **展平**成 token 流，并在末尾追加 EOS：

```
a1 b5 c9 d0 | a8 b3 c1 d0 | EOS
└─ 物品 A ─┘   └─ 物品 B ─┘
```

- 每个物品固定占 4 个位置 token；历史最多保留 20 个物品，所以输入最长为 `20×4+1=81`。
- Decoder 的目标是下一物品的 4 个 token 加 EOS，共 5 个位置。
- 当前实现使用 Hugging Face T5 的相对位置偏置，没有额外实现“同一物品四个 token 共享位置编码”。

### 2.2 两种骨干架构

| | Encoder–Decoder（本项目 T5 式模型） | Decoder-only（扩展方向） |
|---|---|---|
| 结构 | 编码器读历史 + 解码器生成 | 单塔因果 Transformer，直接续写 |
| 注意力 | 编码器双向，解码器因果 | 全程因果 |
| 代表工作 | TIGER | Meta HSTU、GPT 式 |
| 优点 | 结构清晰，历史一次读完 | 简洁、易扩展、适合长序列 |
| 备注 | 本课题主线 | HSTU 首次在推荐场景验证了 Scaling Law |

### 2.3 训练目标

**Next Token Prediction + 交叉熵**。四个物品 token 与 EOS 共五个预测位置，每个位置输出 1,027 个 logits。

训练标签包含 EOS，因此 EOS 位置也计算损失；BOS 只作为 Decoder 起始输入，不作为预测标签。标签补齐位置使用 `-100`，不计入损失。

### 2.4 本环节的坑

- 序列构造方式必须明确并写进报告（怎么拼、位置怎么给、损失在哪些位置算）。
- 学习率、batch size、warmup 等超参要完整记录，配一键复现脚本。
- 训练日志 + 断点续训（服务器 SSH 会断，长任务一律 `tmux`）。

## 3. 环节三：约束解码与偏好对齐

### 3.1 为什么需要约束

前三位量化码的组合空间是 `256³ ≈ 1677 万`，而目录只有 3,416 个物品，因此绝大部分组合不对应真实物品。

模型可能生成 `<a137><b42><c99>`：三个 token 都合法，但拼起来对应不上任何真实物品，翻译回去是空的。这个比例就是**非法生成率**。

### 3.2 Trie 约束解码

把所有真实物品的标识符建成一棵**前缀树**，生成每一步只在树上存在的分支里选，其余分支概率置为 `−∞`。

效果：
- 输出**必然是真实物品**。
- 搜索空间从 `1677 万` 降到**物品总数**。

### 3.3 Beam Search

不要贪心地每步只取最大概率，而是保留 top-B 条候选路径，最后按**累积对数概率**排序取 top-k。

- `B` 一般取 10–50（要调，记进超参表）。
- 约束解码和 Beam Search 是**配合使用**的：每步扩枝时先按 Trie 剪掉非法分支，再保留 top-B。

### 3.4 偏好对齐（后续扩展方向，当前未实现）

**为什么需要**：交叉熵训练只让模型「模仿历史行为」，但推荐目标是「让用户满意」，两者不一致（曝光偏差、流行度偏差）。

**怎么做**：
1. 定义奖励：点击 / 购买 / 停留时长等真实反馈。
2. 策略优化：PPO / DPO / GRPO 微调生成模型，让它更倾向于生成高奖励序列。
3. 参考工作：OneRec（快手，工业落地 + 迭代式偏好对齐）。

**定位**：属于阶段四的「改进探索」，是拿「优秀」的加分项，不是必做项。

### 3.5 本环节的坑

- **约束解码前后要量化对比**（非法生成率、指标变化），不能只说「有效」。
- 加了约束后指标反而可能下降（搜索空间变小），要如实报告并分析。

## 4. 完整走一遍（把三阶段串起来）

**场景**：用户最近观看了 `Toy Story` → `A Bug's Life` → `Antz`。

| 步骤 | 发生什么 | 属于 |
|---|---|---|
| 1 | 三个物品的标题分别过编码器 → 三个语义向量 | ① |
| 2 | 向量过 RQ-VAE 并消歧 → 每部电影得到唯一四位语义 ID | ① |
| 3 | 历史语义 ID 按位置映射为 token，展平后追加 EOS | ② |
| 4 | 模型前向 → 在 Decoder 的每个位置输出 1,027 个 logits | ② |
| 5 | 第一步：在 Trie 的「根的孩子」里选 → 概率最高的合法码字是 `a137` | ③ |
| 6 | 第二步：走到 `a137` 节点，在它的孩子里选 → `b42` | ③ |
| 7 | 第三步：走到 `a137→b42` 节点，在它的孩子里选 → `c88` | ③ |
| 8 | 查映射表反解 → 得到目录中的真实电影 | ① 的表 |
| 9 | Beam Search 保留 top-B 条路径，重复 5–7 → 得到 top-10 推荐列表 | ③ |

注意第 5–7 步：**每生成一个 token，都要查一次 ① 建好的那棵树**。这就是三个环节真正的「串联点」。

---

## 5. 复习用：三句话

1. **环节一**：码本是把连续物品向量压成有限几个「词」的词典；残差量化让词典变成多层，用小词表撬动大组合空间；塌缩是这套机制自带的病，要主动监控。
2. **环节二**：把用户历史展平成 token 流，用 T5 式 Encoder–Decoder 预测下一物品的四位标识符与 EOS。
3. **环节三**：动态 Trie 保证路径对应真实且未见物品，Beam Search 在合法路径中保留高分候选。
